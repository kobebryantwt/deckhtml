DeckUse does not modify the source PPTX directly. Start by creating a workspace, then use `inspect` or `query` to understand what the CLI can address before sending a mutation.

## Create a workspace

```bash
deckuse init input.pptx ./workspace --json
```

A successful initialization returns the normalized workspace path, source format, current revision, package checksum, and detected capabilities. This shortened response keeps the fields most integrations use first:

```json
{
  "ok": true,
  "value": {
    "schemaVersion": "1.0",
    "workspaceId": "/absolute/path/workspace",
    "format": "pptx",
    "source": "/absolute/path/input.pptx",
    "revision": "mssob1ss-2943b374",
    "files": [
      {
        "path": "package.pptx",
        "mediaType": "application/vnd.openxmlformats-officedocument.presentationml.presentation",
        "checksum": "..."
      }
    ],
    "metadata": { "capabilities": { "slides": { "add": true, "duplicate": true, "remove": true } } }
  },
  "diagnostics": []
}
```

The workspace contains its own editable package and index. Reuse it for later commands; do not run `init` again before every query or change.

## Inspect the document

```bash
deckuse inspect ./workspace --depth 2 --json
```

`inspect` returns two main sections:

- `document.format`, `document.revision`, and `document.capabilities` describe the current workspace.
- `elements` contains every indexed slide, shape, text box, picture, table, chart, note, layout, master, and theme entry that DeckUse discovered.

An indexed slide has this shape:

```json
{
  "ref": {
    "documentId": "/absolute/path/workspace",
    "elementId": "slide:256",
    "path": "/ppt/slides/slide1.xml",
    "revision": "mssob1ss-2943b374"
  },
  "kind": "slide",
  "partUri": "/ppt/slides/slide1.xml",
  "slideId": "256",
  "name": "Slide 256",
  "location": {
    "slideId": "256",
    "partUri": "/ppt/slides/slide1.xml"
  }
}
```

The PPTX adapter currently returns its complete flat index. `--depth` accepts `0` through `100`, but does not prune that flat list.

## Query for candidates

Use `query` when you know the type, text, name, slide ID, or element ID you need:

```bash
deckuse query ./workspace 'kind=textbox hasText=true' --limit 100 --json
deckuse query ./workspace 'text=Revenue' --json
deckuse query ./workspace 'text~=^FY20[0-9]{2}$' --limit 1000 --json
deckuse query ./workspace 'slide=256 kind=picture' --json
```

`--limit` defaults to `100` and accepts up to `10000`. A successful query returns an array in `value`; an empty array is a successful query with no matches.

One text-box match has this shape:

```json
{
  "ref": {
    "documentId": "/absolute/path/workspace",
    "elementId": "256:5",
    "path": "/ppt/slides/slide1.xml#256:5",
    "revision": "mssob1ss-2943b374"
  },
  "kind": "textbox",
  "partUri": "/ppt/slides/slide1.xml",
  "slideId": "256",
  "parentId": "slide:256",
  "location": {
    "slideId": "256",
    "partUri": "/ppt/slides/slide1.xml",
    "ancestorIds": [],
    "cNvPrId": "5"
  },
  "name": "TextBox 4",
  "text": "Q2 FY2025 · APRIL – JUNE 2025",
  "transform": {
    "x": 566928,
    "y": 2084831,
    "width": 10607040,
    "height": 365760
  }
}
```

See [Selectors and Element References](/deckuse/selectors) for every string selector and the structured selector accepted by the Node.js API.

## Decide whether a match is safe to change

Before building a targeted command, check:

1. `value` contains the number of elements your workflow expects.
2. `kind`, `slideId`, `name`, and `text` identify the intended object.
3. The returned `ref` comes from the current workspace, not from documentation or another presentation.
4. The `revision` is still current when the mutation runs.

Slide IDs such as `256` are stable presentation IDs, not one-based slide numbers. Query `kind=slide` to discover them.

<Warning>
  Every persisted mutation creates a new workspace revision. A reference that includes an older revision will then fail with `TRANSACTION_CONFLICT`. Query again before the next targeted mutation, or place related operations in one reviewed atomic batch.
</Warning>

## Inspect or query?

| Need | Command |
| --- | --- |
| Discover document capabilities or review the whole index | `inspect` |
| Find a manageable candidate set | `query` |
| Target one known element for a mutation | `query`, then reuse its `ref` |
| Read one element through application code | Node.js `getText` command |

Continue with [Apply and Export](/deckuse/cli/apply-and-export) after you have reviewed the intended targets.
