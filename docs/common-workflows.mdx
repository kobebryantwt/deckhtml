Start with the action the agent must perform and the result the application expects. Each DeckFlow product exposes an independent contract, so an agent can call one product for a focused task or combine several products when the workflow genuinely needs several results.

## Five common agent scenarios

<CardGroup cols={2}>
  <Card title="Screen an incoming attachment" icon="shield-halved" iconType="solid" href="/deckprobe/overview" cta="Use DeckProbe" arrow>
    An intake agent verifies the actual format, counts, encryption, structure, and embedded assets before accepting or routing a file. It receives local, machine-readable facts without uploading the document.
  </Card>
  <Card title="Give an agent a visual view" icon="eye" iconType="solid" href="/deckrender/guides/render-images" cta="Use DeckRender" arrow>
    A multimodal or review agent turns a supported document into page images, thumbnails, PDF, or video. It receives written artifacts plus a structured result describing those files.
  </Card>
  <Card title="Prepare documents for search and reasoning" icon="file-lines" iconType="solid" href="/deckops/parse" cta="Use DeckOps" arrow>
    A knowledge agent parses supported documents into Markdown or format-specific structured content for indexing, retrieval, summarization, and downstream reasoning.
  </Card>
  <Card title="Maintain an existing presentation" icon="pen-to-square" iconType="solid" href="/deckuse/quick-start" cta="Use DeckUse" arrow>
    A presentation-maintenance agent finds specific slides or elements, applies approved content and property changes locally, validates the package, and exports another editable PPTX.
  </Card>
  <Card title="Create a presentation from application data" icon="code" iconType="solid" href="/deckhtml/quick-start" cta="Use DeckHTML" arrow>
    A generation agent turns templates, application data, or generated HTML/SVG into an editable PPTX or page PNGs, with diagnostics for editability and visual fallbacks.
  </Card>
</CardGroup>

## What the agent receives

| Agent task | Product | Primary result | Execution boundary |
| --- | --- | --- | --- |
| Decide whether and where a file should continue | DeckProbe | Schema v2 document facts and evidence | Local |
| See or deliver the visual document | DeckRender | Images, PDF, video, and `RenderResult` | Explicit local or cloud engine |
| Read, index, extract, or transform content | DeckOps | Markdown, format-specific JSON, or converted files | Cloud |
| Apply known changes to an existing PPTX | DeckUse | Updated editable PPTX and operation results | Local |
| Build a new deck from HTML or SVG | DeckHTML | Editable PPTX or page PNGs with conversion diagnostics | Local or cloud |

## Typical task sequence

The products do not invoke one another automatically. The application or agent decides which result is needed at each step:

| Workflow | Sequence | Why combine them |
| --- | --- | --- |
| Safe multimodal attachment review | DeckProbe → application policy → DeckRender | Verify the attachment locally, then render only accepted files for visual review or model input. |
| Controlled document ingestion | DeckProbe → application policy → DeckOps | Check identity and security facts before uploading accepted files for parsing or conversion. |
| Update and visually verify a presentation | DeckUse → DeckRender | Modify the editable PPTX locally, then render the exported file for visual QA. |
| Turn source material into a new presentation | DeckOps → application logic → DeckHTML | Parse source content, shape it into application data or HTML, then generate a new deck. |

<Note>
  Persist each product's result independently. A probe report, parse result, rendered artifact, PPTX edit, and HTML conversion report have different retry, caching, and validation rules.
</Note>

## Build the workflow

<Steps>
  <Step title="Define the agent's final result">
    Choose facts, visual artifacts, structured content, an updated PPTX, or a newly generated deck.
  </Step>
  <Step title="Confirm the data boundary">
    DeckProbe and DeckUse run locally. DeckOps runs in the cloud. DeckRender explicitly selects `local`, `cloud`, or local-first `auto`; DeckHTML depends on its selected mode.
  </Step>
  <Step title="Run one product end to end">
    Verify its input, result, errors, and authentication before adding another product to the workflow.
  </Step>
  <Step title="Compose only required results">
    Add another product only when the agent needs a second independent artifact or decision.
  </Step>
</Steps>
