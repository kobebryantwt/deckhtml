All Deckflow business scenarios reuse the same API foundation. Before looking at generation, translation, revamp, or tool-specific guides, it helps to understand the common request model first.

## Base URL

```text
https://app.deckflow.com/api
```

## Required headers

| Header | Required | Purpose |
|---|---|---|
| `Authorization` | Yes | Use `Bearer <YOUR_API_KEY>` for every authenticated API request. |
| `Content-Type` | Yes for submit | Use `multipart/form-data` when creating a task through `POST /tools/tasks`. |

## Common async task flow

<Steps>
  <Step title="Authenticate">
    Send your API key in the `Authorization` header.
  </Step>
  <Step title="Submit a task">
    Upload one or more files, choose a `type`, and provide any scenario-specific JSON through `params`.
  </Step>
  <Step title="Track progress">
    Store the returned task ID and query it through `GET /tools/tasks/{id}`, or subscribe through SSE by sending `response-event-stream: yes`.
  </Step>
  <Step title="Download the result">
    Once the task is complete, either use the `result.url` returned in the task payload or call the dedicated download endpoint directly.
  </Step>
</Steps>

## Common submit fields

These fields are reused across generation, translation, revamp, and tool APIs:

| Field | Required | Meaning |
|---|---|---|
| `spaceId` | No | Target workspace or space identifier. |
| `files` | Scenario-dependent | Source files to process. Some workflows require one file, some allow multiple, and some merge workflows require at least two. |
| `type` | Yes | Business scenario or tool identifier such as `generation`, `translation`, `revamp`, or `convertor.html2pptx`. |
| `name` | No | Human-readable task name shown in task history or dashboards. |
| `notifyURL` | No | Webhook callback URL for task status changes. |
| `params` | Usually yes | A JSON string containing scenario-specific parameters. |

## Status handling

- Newly created tasks typically start in `pending` or another non-terminal state.
- Continue polling until the task becomes `completed` or `failed`.
- Successful tasks return result metadata and a download URL.
- Failed tasks return error information that should be logged or surfaced upstream.
