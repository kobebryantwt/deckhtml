Choose by the artifact your application must receive and whether the original document needs to remain editable. The same source file can travel through several products for different purposes.

## Product comparison

| Product | Start with | Produces | Runs | Does not replace |
| --- | --- | --- | --- | --- |
| DeckProbe | Existing PDF, Office, or modern iWork document | Schema v2 target evidence and measured probe cost | Native Rust CLI; WebAssembly source awaiting corrected npm artifact | Full content parsing, rendering, or editing |
| DeckRender | Supported document, URL, or stdin | Images, PDF, or video | Local, passthrough, or cloud route | Structured content extraction or source editing |
| DeckOps | File, URL, or uploaded file ID | Format-specific parse results, Markdown, or generated files | Deckflow cloud tasks | Local-only inspection or editable source mutation |
| DeckUse | Existing PPTX | Updated PPTX | Local Node.js workflow | DOCX/XLSX/Keynote editing or new deck authoring |
| DeckHTML | HTML, SVG, URL, or stdin | PPTX, PNG, and conversion diagnostics | Local browser or cloud task | General-purpose conversion of existing Office files |

## Common decisions

<AccordionGroup>
  <Accordion title="DeckProbe or DeckOps?">
    Use **DeckProbe** when verified document-level facts are the final result or are needed before accepting and routing a file. Use **DeckOps** when you need page and element content, Markdown, semantic extraction, or a generated file. A deeper DeckProbe level still returns target evidence, not a DeckOps parse result.
  </Accordion>
  <Accordion title="DeckRender or DeckOps?">
    Use **DeckRender** when your application needs a predictable visual artifact and does not want to manage underlying cloud task names, multi-step routes, page naming, or downloads. Use **DeckOps** when the task itself is part of a broader parse, extract, convert, or generation workflow.
  </Accordion>
  <Accordion title="DeckUse or DeckHTML?">
    Use **DeckUse** when an existing PPTX is the source of truth and you need to change its current content. Use **DeckHTML** when HTML or SVG is the authoring source and a new PPTX or PNG is the result.
  </Accordion>
  <Accordion title="Can products be combined?">
    Yes. A typical ingestion flow can use DeckProbe to validate a file, DeckOps to parse it, and DeckRender to produce previews. These are separate calls with separate result contracts; Deckflow does not require every workflow to use all products.
  </Accordion>
</AccordionGroup>

## Choose by scenario

| Scenario | Recommended path |
| --- | --- |
| Reject encrypted or macro-enabled uploads before processing | DeckProbe → application policy |
| Generate slide thumbnails for a review UI | DeckRender |
| Convert a PPTX to PDF and also extract notes or layout data | DeckOps |
| Read a document as Markdown for RAG | DeckOps Parse |
| Replace a customer name throughout an existing PPTX | DeckUse |
| Generate a branded, editable deck from a web layout | DeckHTML |
| Validate, parse, and preview one uploaded document | DeckProbe → DeckOps → DeckRender |

<Warning>
  Product names describe responsibility, not identical format coverage or package availability. Check the selected product's format matrix and availability warning before designing a workflow; DeckProbe JavaScript and DeckOps Parse source APIs currently await corrected public artifacts.
</Warning>
