The five products solve different document tasks. Choose by the result your application needs rather than by the source file alone.

| Product | Best for | Execution | Primary result |
| --- | --- | --- | --- |
| DeckProbe | Fast inspection, upload checks, routing, and policy decisions | Native Rust locally or Browser JS SDK | Target evidence with confidence and measured cost |
| DeckRender | Focused document rendering | Cloud rendering through an SDK | Page or slide visuals |
| DeckOps | Full document understanding and transformation | Cloud execution through an SDK | Document IR, semantic extraction, converted files, or renders |
| DeckUse | Source-aware Office file manipulation | Local library workflow | Updated Office source file |
| DeckHTML | HTML-native deck authoring | Local and cloud paths | Presentation artifacts generated from HTML |

## DeckProbe or DeckOps?

This is the most common boundary:

- Choose **DeckProbe** when document-level facts are the final result: verified format, metadata, counts, security signals, confidence, and probe cost.
- Choose **DeckOps** when the application needs page and element structure, a unified Document IR, semantic Extract, format Convert, or combined Render.
- DeckProbe's `deep` level still returns target evidence; it does not produce the DeckOps Document IR.

## DeckRender or DeckOps?

- Choose **DeckRender** when rendered pages or slides are the only required output.
- Choose **DeckOps** when rendering is part of a broader flow that also needs probing, parsing, extraction, or conversion.

## DeckOps or DeckUse?

- Choose **DeckOps** to normalize different formats into an IR and create derived results.
- Choose **DeckUse** when a supported Office file remains the editable artifact and existing elements must be modified or deleted.

## When to use DeckHTML

Choose DeckHTML when HTML is the source of slide structure and visual design. It is a specialized authoring path rather than a general parser for existing office documents.
