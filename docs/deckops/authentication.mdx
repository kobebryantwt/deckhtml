DeckOps supports three identities. All modes execute on Deckflow cloud and therefore upload task inputs.

| Mode | Header | Start behavior | Recommended use |
| --- | --- | --- | --- |
| API key | `Authorization: Bearer <key>` | Tasks start automatically | Production services and CI |
| User token | `X-Auth-Token: <token>` | Tasks start automatically | Interactive applications and signed-in CLI use |
| Guest UUID | Guest identity generated by the client | Low-level tasks require `tasks.start()` | Evaluation and limited experiments |

## API key

Pass the key when creating a TypeScript client. Keep it in a server-side secret store; do not ship it in browser bundles.

```ts
const deck = createDeck({ apiKey: process.env.DECKOPS_API_KEY });
```

## User token

The DeckOps CLI can open a browser login flow and store a token in `~/.deckops/config.json`:

```bash
deckops login
```

SDK clients may pass the returned token and an optional space ID explicitly. Do not commit the configuration file.

## Guest execution

A guest low-level task is created in `pending` state. Start it explicitly, then wait and download:

```ts
const task = await deck.convertPptToPdf({ files: ['./slides.pptx'] });
await deck.tasks.start(task.id);
const completed = await deck.tasks.wait(task.id);
const result = await deck.tasks.down(completed.id);
```

The Node.js CLI performs this guest start automatically. The TypeScript and Go SDKs expose `tasks.start`; the current Python SDK does not, so use authenticated execution from Python.

<Warning>
  The high-level `parse()` and `parseDetailed()` facades create and wait for a task without guest-starting it. Configure an API key or user token for those methods.
</Warning>

## Production checklist

- Store API keys and tokens in your deployment secret manager.
- Configure a stable space ID when tasks must share one workspace.
- Treat task IDs and downloaded results as application data.
- Handle authentication failures separately from task failures and timeouts.
