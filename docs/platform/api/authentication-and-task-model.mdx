All DeckFlow business scenarios reuse the same API foundation. Before looking at generation, translation, revamp, or tool-specific guides, it helps to understand the common request model first.

## Base URL

```text
https://app.deckflow.com/api
```

## Get an API key

<Steps>
  <Step title="Open DeckFlow Settings">
    Sign in to DeckFlow and open [API Key Settings](https://app.deckflow.com/start#settings).
  </Step>
  <Step title="Create and copy an API key">
    Configure an API key in Settings, then copy it to a secure secret store used by your server or development environment.
  </Step>
  <Step title="Set the environment variable">
    ```bash
    export DECKFLOW_API_KEY="YOUR_API_KEY"
    ```
  </Step>
</Steps>

<Warning>
  Treat the API key as a server-side secret. Do not embed it in browser code, commit it to a repository, or expose it in logs.
</Warning>

## Required headers

| Header | Required | Purpose |
|---|---|---|
| `Authorization` | Yes | Use `Bearer <YOUR_API_KEY>` for every authenticated API request. |
| `Content-Type` | Yes for submit | Use `multipart/form-data` for `POST /tools/tasks`; let the HTTP client add the multipart boundary. |

```bash
curl 'https://app.deckflow.com/api/tools/tasks/TASK_ID' \
  --header "Authorization: Bearer $DECKFLOW_API_KEY"
```

## Common async task flow

<Steps>
  <Step title="Authenticate">
    Read the API key from your secret store and send it in the `Authorization` header.
  </Step>
  <Step title="Submit a task">
    Upload one or more files, choose a `type`, and provide any scenario-specific JSON through `params`.
  </Step>
  <Step title="Track progress">
    Store the returned task ID and query it through `GET /tools/tasks/{id}`, or subscribe through SSE by sending `response-event-stream: yes`.
  </Step>
  <Step title="Download the result">
    Once the task is `completed`, call `GET /tools/tasks/{id}/download` and read the result URL from `target`.
  </Step>
</Steps>

## Common submit fields

These fields are reused across generation, translation, revamp, and tool APIs:

| Field | Required | Meaning |
|---|---|---|
| `spaceId` | No | Target workspace or space identifier. |
| `files` | One of `files` or `fileIds` | Source files uploaded in this request. Repeat the multipart field to send multiple files. |
| `fileIds` | One of `files` or `fileIds` | IDs of files already available in DeckFlow. Send an array through a client that preserves repeated multipart values. |
| `type` | Yes | Business scenario or tool identifier such as `generation`, `translation`, `revamp`, or `convertor.html2pptx`. |
| `name` | No | Human-readable task name shown in task history or dashboards. |
| `notifyURL` | No | Webhook callback URL for task status changes. |
| `params` | Usually yes | A JSON string containing scenario-specific parameters. |

## Status handling

- Newly created tasks typically start in `pending` or another non-terminal state.
- Continue polling until the task becomes `completed` or `failed`.
- A `201` create response only means the task was accepted; it does not mean processing succeeded.
- A completed task can be passed to the result endpoint to obtain the output URL and metadata.
- A failed task can have no separate error payload in its detail response. Record the task ID and terminal status for diagnosis.

<Warning>
  In the verified zero-credit behavior, the API accepted the request with `201`, reported `credits: 0`, and later changed the task to `failed`. It did not return `429`. Always evaluate the terminal task status instead of treating task creation as completion.
</Warning>
