# Product model

The product names describe what happens to a document. Integration surfaces such as CLI, SDK, API, and MCP describe how a caller reaches that capability.

| Product | Direction | Primary responsibility | Does not own |
| --- | --- | --- | --- |
| DeckProbe | Read-only | Target-driven facts with evidence, confidence, and measured probe cost | Element-level content extraction, rendering, conversion, or mutation |
| DeckRender | Source to visual output | Cloud rendering through an SDK surface | Parsing into IR or source editing |
| DeckOps | Source to IR and derived results | Probe, Parse into Document IR, Extract, Convert, and Render in one cloud runtime | Writing changes back through a source-aware editing model |
| DeckUse | Bidirectional | Manipulate supported Office source files | General document conversion or HTML-first authoring |
| DeckHTML | HTML-native deck engine | Generate presentation artifacts from HTML through local and cloud paths | General-purpose inspection or manipulation of existing documents |

## Typical composition

1. Use DeckProbe to request only the document facts needed for routing and policy decisions.
2. Use DeckRender for a focused render path, or DeckOps when the workflow needs a unified IR, semantic extraction, conversion, or the combined runtime.
3. Use DeckUse to manipulate a supported Office source file, and DeckHTML when HTML is the native authoring source for a deck.

<Warning>
  Do not infer a product contract from an interface name. For example, an MCP server may expose tools backed by more than one product. The capability and product boundary are authoritative; the transport is secondary.
</Warning>
