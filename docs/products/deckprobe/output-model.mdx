# Output model

DeckProbe uses a stable Schema v2 report envelope, but the facts inside the report are target-driven. It does not promise one fixed flat field list for every document format.

## Stable report envelope

A full probe report contains:

| Field | Meaning |
| --- | --- |
| `schema_version` | Report contract version; currently `2` |
| `tool_version` | DeckProbe version that produced the report |
| `status` | `ok`, `partial`, or `error` |
| `input` | Display name, source kind, and physical file size |
| `driver` | Selected format driver and profile |
| `results` | Requested target IDs mapped to evidence records |
| `execution` | Probe level, selected paths, estimated and actual cost, and unresolved targets |
| `diagnostics` | Structured warnings and diagnostic messages |

Each result records its `target`, `status`, optional `value`, `confidence`, `confidence_score`, selected `path`, and evidence `source`. A target can be `resolved`, `estimated`, `planned`, `unknown`, `unsupported`, `invalid`, `budget_exceeded`, or `failed`.

```json
{
  "schema_version": 2,
  "status": "ok",
  "driver": {
    "id": "powerpoint",
    "profile": "pptx"
  },
  "results": {
    "powerpoint.slide_count": {
      "target": "powerpoint.slide_count",
      "status": "resolved",
      "value": 42,
      "confidence": "exact",
      "confidence_score": 1,
      "path": "powerpoint.presentation_xml",
      "source": "ppt/presentation.xml"
    }
  }
}
```

<Note>
  The example is abbreviated to highlight the target evidence. A complete report also includes `tool_version`, `input`, `execution`, and `diagnostics`.
</Note>

## Common base and format extensions

The implementation registers targets in three scopes:

- `Common`: cross-format identity, metadata, security, and quality targets such as `document.format`, `document.author`, and `security.encrypted`.
- `Office`: facts shared by Office drivers, such as `office.document_kind`, package entry count, and OOXML conformance.
- `Format`: namespaced facts owned by a driver, such as `powerpoint.slide_count`, `excel.sheet_names`, `pdf.xref_type`, or `keynote.slide_size`.

This means the output contract has a stable outer shape and a shared vocabulary, while each verified format can expose additional facts through its own namespace.

## Probe depth and cost

DeckProbe exposes `header`, `metadata`, and `deep` levels. The level limits which targets and paths are available; it does not turn the result into a DeckOps-style element model.

Every run is bounded by physical-read, decompression, archive-entry, and wall-clock budgets. The planner chooses the cheapest valid path that meets the requested confidence, and the report records estimated and actual I/O cost.

## Current animation boundary

There is no generic `contains_animation` or `has_animation` target in the current implementation.

- The PowerPoint driver does not currently expose animation or transition targets.
- The Keynote driver exposes format-specific counts for slides with builds and slides with transitions: `keynote.slides_with_builds_count` and `keynote.slides_with_transitions_count`.
- These Keynote values are document-level statistics, not extracted animation timelines or effect definitions.

Detailed animation types, triggers, ordering, and object relationships belong to the [DeckOps Document IR](/products/deckops/document-ir).

## No `complexity` field

`complexity` is not part of the current target registry or Schema v2 contract. Consumers should derive their own complexity classification from supported facts such as file size, page or slide count, package entry count, and asset counts if their workflow needs one.

## Discover the live contract

Use DeckProbe itself when an integration needs the exact capabilities of the installed version:

```bash
deckprobe --pretty formats
deckprobe --pretty targets --format pptx
deckprobe schema
```

The repository's [tracked JSON Schema](https://github.com/deckflow/deckprobe/blob/main/docs/deckprobe-report.schema.json) is the authoritative machine-readable report contract.
