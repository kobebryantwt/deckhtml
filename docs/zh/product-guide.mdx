选择时先看应用必须得到什么产物，以及原始文档是否需要继续保持可编辑。同一个源文件可以因为不同目的进入多个产品。

## 产品对比

| 产品 | 输入 | 产物 | 执行位置 | 不替代什么 |
| --- | --- | --- | --- | --- |
| DeckProbe | 已有 PDF、Office 或现代 iWork 文档 | Schema v2 Target 证据和实际探测成本 | 原生 Rust CLI；WebAssembly 源码等待修正 npm 产物 | 完整内容解析、渲染或编辑 |
| DeckRender | 支持的文档、URL 或标准输入 | 图片、PDF 或视频 | 本地、透传或云端路径 | 结构化内容提取或源文件编辑 |
| DeckOps | 文件、URL 或已上传的 File ID | 格式专属解析结果、Markdown 或生成文件 | Deckflow 云端任务 | 纯本地检查或可编辑源文件修改 |
| DeckUse | 现有 PPTX | 修改后的 PPTX | 本地 Node.js 工作流 | DOCX/XLSX/Keynote 编辑或新建 Deck |
| DeckHTML | HTML、SVG、URL 或标准输入 | PPTX、PNG 和转换诊断 | 本地浏览器或云端任务 | 对现有 Office 文件的通用转换 |

## 常见选择

<AccordionGroup>
  <Accordion title="DeckProbe 还是 DeckOps？">
    最终只需要经过验证的文档级事实，或需要在接收、路由文件前判断风险时，使用 **DeckProbe**。需要页面和元素内容、Markdown、语义提取或生成文件时，使用 **DeckOps**。提高 DeckProbe 的探测级别仍然只会得到 Target 证据，不会变成 DeckOps 的解析结果。
  </Accordion>
  <Accordion title="DeckRender 还是 DeckOps？">
    应用只需要稳定的视觉文件，不希望管理底层任务名、多步路径、页面命名和下载时，使用 **DeckRender**。渲染属于更大的解析、提取、转换或生成流程时，直接使用 **DeckOps**。
  </Accordion>
  <Accordion title="DeckUse 还是 DeckHTML？">
    现有 PPTX 是事实源，并需要修改其中已有内容时，使用 **DeckUse**。HTML 或 SVG 是创作源，并要生成新的 PPTX 或 PNG 时，使用 **DeckHTML**。
  </Accordion>
  <Accordion title="产品可以组合使用吗？">
    可以。典型接入流程可以先用 DeckProbe 校验文件，再用 DeckOps 解析内容，最后用 DeckRender 生成预览。三者是独立调用并返回不同契约，Deckflow 不要求所有流程都使用全部产品。
  </Accordion>
</AccordionGroup>
