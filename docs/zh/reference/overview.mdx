Deckflow API 的底层组织方式，其实就是一套通用的异步任务流程。无论是文档生成、翻译、焕新，还是工具类文件处理，都会复用同一套任务提交、任务查询和结果下载模式。

在参考文档这一层，最重要的公共接口是：

- `POST /tools/tasks`
- `GET /tools/tasks/{id}`
- `GET /tools/tasks/{id}/download`

因此，这一节会分成两层来讲：

- **核心接口**：如何提交任务、查询状态、下载结果
- **场景文档**：不同业务场景下该传什么 `type`、`files` 和 `params`

<Note>
  你刚才提到的 `shared model` 不是 Deckflow 官方原词。这里更准确的说法应该是“通用异步任务流程”或“统一任务模型”，对应官方文档里的“接口调用模型 / 通用 API 与认证”。
</Note>

## 通用异步任务流程

Deckflow 在不同业务场景下都遵循相同生命周期：

- 通过 `Authorization: Bearer <YOUR_API_KEY>` 完成认证
- 以 `multipart/form-data` 提交文件、任务类型和 JSON 参数
- 立即拿到任务 ID
- 通过轮询或 SSE 订阅持续跟踪任务状态
- 任务成功后，通过 `result.url` 或专用下载接口获取最终文件
