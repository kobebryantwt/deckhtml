先确定 Agent 要执行的动作，以及应用最终需要的结果。每个 DeckFlow 产品都有独立契约：一个任务只需要一种结果时调用一个产品，确实需要多种结果时再组合调用。

## 五类常见 Agent 场景

  <Card title="检查收到的附件" icon="shield-halved" iconType="solid" href="/zh/deckprobe/overview" cta="使用 DeckProbe" arrow>

  <Card title="为检索和推理准备文档内容" icon="file-lines" iconType="solid" href="/zh/deckops/parse" cta="使用 DeckOps" arrow>

  <Card title="维护现有演示文稿" icon="pen-to-square" iconType="solid" href="/zh/deckuse/quick-start" cta="使用 DeckUse" arrow>

  </Card>
  <Card title="从应用数据生成演示文稿" icon="code" iconType="solid" href="/zh/deckhtml/quick-start" cta="使用 DeckHTML" arrow>

## Agent 会得到什么

| Agent 任务 | 产品 | 主要结果 | 执行边界 |
| --- | --- | --- | --- |
| 判断文件是否继续处理以及进入哪条路径 | DeckProbe | Schema v2 文档事实与证据 | 本地 |
| 查看或交付文档的视觉内容 | DeckRender | 图片、PDF、视频和 `RenderResult` | 显式选择本地或云端引擎 |
| 读取、索引、提取或转换文档内容 | DeckOps | Markdown、格式专属 JSON 或转换文件 | 云端 |
| 对现有 PPTX 执行明确修改 | DeckUse | 修改后仍可编辑的 PPTX 与操作结果 | 本地 |
| 从 HTML 或 SVG 创建新 Deck | DeckHTML | 可编辑 PPTX 或页面 PNG，以及转换诊断 | 本地或云端 |

## 常见组合方式

各产品不会自动调用其他产品。应用或 Agent 应根据每一步所需结果决定是否组合：

| 工作流 | 调用顺序 | 组合原因 |
| --- | --- | --- |
| 安全的多模态附件评审 | DeckProbe → 应用策略 → DeckRender | 先在本地验证附件，再把通过检查的文件渲染成视觉内容供模型或评审界面使用。 |
| 受控的文档入库 | DeckProbe → 应用策略 → DeckOps | 上传前先检查文件身份和安全事实，再解析或转换通过检查的文件。 |
| 修改并检查演示文稿 | DeckUse → DeckRender | 在本地修改可编辑 PPTX，再渲染导出文件进行视觉检查。 |
| 根据源材料生成新演示文稿 | DeckOps → 应用逻辑 → DeckHTML | 解析源内容，由应用整理为数据或 HTML，再生成新的 Deck。 |

<Note>
  请独立保存每个产品的结果。探测报告、解析结果、渲染产物、PPTX 修改结果和 HTML 转换报告具有不同的重试、缓存和校验规则。
</Note>

## 开始构建工作流

<Steps>
  <Step title="确定 Agent 的最终结果">
    在文档事实、视觉产物、结构化内容、修改后的 PPTX 和新生成的 Deck 中选择。
  </Step>
  <Step title="确认数据边界">
    DeckProbe 与 DeckUse 在本地执行，DeckOps 在云端执行；DeckRender 显式选择 `local`、`cloud` 或本地优先的 `auto`，DeckHTML 取决于所选模式。
  </Step>
  <Step title="先跑通一个产品">
    确认它的输入、结果、错误和认证方式，再向工作流中增加其他产品。
  </Step>
  <Step title="只组合实际需要的结果">
    只有 Agent 还需要第二种独立产物或判断时，才增加另一个产品。
  </Step>
</Steps>
