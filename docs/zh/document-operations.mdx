Deckflow 按“对文档执行什么操作”和“向应用返回什么结果”划分产品。以下术语描述的是开发者可直接使用的能力，而不是内部实现层级。

## 能力地图

| 操作 | 作用 | 主要结果 | 产品 |
| --- | --- | --- | --- |
| Probe | 在不构建完整页面模型的情况下，回答文档身份、元数据、结构、安全和资源方面的目标问题 | 带证据的文档事实 | [DeckProbe](/zh/deckprobe/overview) |
| Render | 将支持的文档转换成页面或幻灯片画面 | 图片和预览 | [DeckRender](/zh/deckrender/overview) |
| Parse | 将支持的格式规范化成统一的 Schema 表达 | Document IR | [DeckOps](/zh/deckops/overview) |
| Extract | 读取标题、副标题、图表、演讲者备注和脚注等页面语义结构 | 结构化语义结果 | [DeckOps](/zh/deckops/overview) |
| Convert | 从解析后的源文档生成另一种文档格式 | 转换后的文档 | [DeckOps](/zh/deckops/overview) |
| Manipulate | 修改支持的 Office 源文件，同时保留可编辑的源文件产物 | 更新后的 Office 文件 | [DeckUse](/zh/deckuse/overview) |
| 从 HTML 生成 | 使用 HTML 定义演示文稿的结构和视觉设计 | 演示文稿产物 | [DeckHTML](/zh/deckhtml/overview) |

## 这些操作有什么区别

### 只嗅探，不转换

文档事实就是最终结果时使用 **Probe**。无需渲染文件或构建 Document IR，即可将结果用于上传校验、路由、策略检查、索引判断或界面提示。

### 统一表示并生成派生结果

下游任务需要统一的页面和元素结构时使用 **Parse**。得到 Document IR 后，DeckOps 可以继续完成语义 **Extract**、格式 **Convert** 或组合渲染流程。

### 生成视觉结果

需要页面或幻灯片画面时使用 **Render**。渲染本身不代表已经完成语义提取，也不会修改可编辑的源文件。

### 保留可编辑源文件

修改或删除元素后仍需将现有 Office 文档作为源产物时，使用 **Manipulate**。它不同于生成派生表示或格式转换文件。

### 从 HTML 创作

HTML 用来定义 Deck 结构和视觉设计时，使用“从 HTML 生成”。这是创作流程，而不是分析已有 Office 文件。

需要进一步确认产品边界时，继续阅读[选择产品](/zh/product-guide)。
